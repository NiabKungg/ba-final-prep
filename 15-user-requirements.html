บทที่ 15 · Understanding User Requirements — Use Case vs User Story

เปลี่ยนจาก "product-centric" (ฟีเจอร์ขายได้) เป็น usage-centric (ผู้ใช้ต้องทำอะไรให้สำเร็จ) — เทียบ 2 ตัวหลักคือ Use Case กับ User Story (ควิซ 10)

1. Product-centric vs User-centric vs Usage-centric

🛍️ Product-centric

มองว่า "จะขายอะไร" → Features that sell

👤 User-centric

มองจากมุมผู้ใช้ → User Stories

🎯 Usage-centric

มองจาก "งานที่ผู้ใช้ต้องทำให้สำเร็จ" → Use Cases (necessary functionality)

ทั้ง Use Case และ User Story เปลี่ยนคำถามจาก "อยากให้ระบบทำอะไร" → "ผู้ใช้ต้อง accomplish อะไร"

2. Use Case (ย่อ)

📖 นิยาม

Use case = ลำดับปฏิสัมพันธ์ (sequence of interactions) ระหว่างระบบกับ external actor ที่ทำให้ actor บรรลุผลลัพธ์ที่มีคุณค่า (outcome of value) · ชื่อเขียนแบบ Verb + Object เสมอ (เช่น "Order a product")

วิธีหา actor: ใคร/อะไรได้รับแจ้งเมื่อระบบทำงาน? ใครให้ข้อมูล/บริการแก่ระบบ? ใครช่วยระบบตอบสนอง-เสร็จงาน?

3. User Story

📖 นิยาม + เทมเพลต

User story = คำอธิบายฟีเจอร์แบบ "สั้น ง่าย" จากมุมมองของผู้ที่ต้องการความสามารถนั้น (มักเป็นผู้ใช้/ลูกค้า) — ใช้ใน Agile

As a <type of user>, I want <some goal> so that <some reason>

ตัวอย่างครบ: "As a customer, I want to update my customer profile so that future purchases are billed to a new credit card number."

  • ส่วน user class สัมพันธ์กับ Primary Actor ของ use case · rationale ไปอยู่ใน brief description ของ use case ได้
  • user class ไม่จำเป็นต้องเป็นมนุษย์ (bot ก็ได้)

4. เทียบกันแบบตรงไปตรงมา (ออกสอบชัด ๆ)

User Story 📝Use Case 📖
รูปแบบประโยคเดียว 3 ส่วน (user-goal-reason)ลำดับ interaction ละเอียด (มีเทมเพลต/บทสนทนา)
จุดแข็งเรียบง่าย กระชับ — ทำเร็ว ทุกคนเข้าใจให้โครงสร้าง+บริบท — BA ใช้นำการสนทนา elicit เจาะลึกการโต้ตอบ user-system
จุดอ่อนขาดโครงสร้างและบริบท → ทีมง่ายที่จะพลาด acceptance testsใหญ่กว่า ต้องลงแรงกว่า (แต่ครบกว่า)
เจาะลึกถึงไหนระดับ "อยากได้อะไร"ระดับ "ผู้ใช้จินตนาการมือปฏิสัมพันธ์กับระบบอย่างไร" (แต่ไม่ลง design specifics — แค่ภาพในหัวผู้ใช้)

Core Distinction — ทั้งสองนำไปสู่ FR และการทดสอบอย่างไร

🎯 ข้อสอบถูก/ผิดที่ชอบหลอก
  • ❌ "เอาคำขอผู้ใช้ไปเขียน FR ส่งโปรแกรมเมอร์ได้ทันที" — ต้องวิเคราะห์/ทำให้ชัดก่อนเสมอ
  • ❌ "User Requirements คือขั้นสุดท้ายของ BA ไม่ต้องแปลงเป็น FR/acceptance tests"
  • ❌ "Use Case ต้องใส่รายละเอียด design เสมอ" / ❌ "ชื่อ user story ขึ้นต้น Verb+Noun เสมอ" (นั่นคือกฎของ use case!)
  • ✅ User story บอก user class + rationale · ✅ Persona ช่วยเมื่อไม่มีผู้ใช้จริง

สรุปท้ายบท

✅ ต้องจำให้ได้
  1. Usage-centric = ถามว่า "ผู้ใช้ต้องทำอะไรให้สำเร็จ" ไม่ใช่ "ระบบทำอะไรได้"
  2. Use Case: ลำดับ interaction กับ actor จนได้ outcome of value · ชื่อ Verb+Object
  3. User Story: "As a…, I want…, so that…" — สั้น กระชับ แต่ขาดโครงสร้าง/บริบท (เสี่ยงพลาด acceptance tests)
  4. Use Case ให้โครงสร้าง+บริบท นำการสนทนาได้ดี — แต่ไม่ลง design
  5. ทั้งคู่ต้องแปลงต่อเป็น FR + acceptance criteria เสมอ
