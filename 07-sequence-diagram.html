บทที่ 7 · Sequence Diagram (แผนภาพลำดับ)

BPMN บอกว่า "ธุรกิจทำงานอย่างไร" ส่วน Sequence Diagram บอกว่า "ระบบกับผู้ใช้คุยกันอย่างไร ตามลำดับเวลา" — เป็นสะพานจาก Use Case สู่โค้ด (อยู่ในชุด Requirements/Analysis Model)

1. Sequence Diagram คืออะไร ใช้เมื่อไร

📖 นิยาม

Sequence diagram เป็น interaction diagram ชนิดหนึ่ง — อธิบายว่า กลุ่มของ objects ทำงานร่วมกันอย่างไร และในลำดับใด (how—and in what order) บางครั้งเรียก event diagrams หรือ event scenarios

ใช้ทำอะไร: นักพัฒนาและนักธุรกิจใช้เข้าใจ requirements ของระบบใหม่ หรือบันทึกกระบวนการที่มีอยู่ · แสดงปฏิสัมพันธ์ของ objects ใน scenario หนึ่ง ๆ ของ Use Case · วางแผน/ทำความเข้าใจฟังก์ชันของระบบเชิงลึก

💭 เปรียบเทียบให้เห็นภาพ

ลองนึกถึง บทสนทนาแชท: แต่ละคน (object) มี "คอลัมน์" ของตัวเอง เวลาไหลจากบนลงล่าง และข้อความ (message) คือลูกศรที่ยิงไปหากัน — อ่าาศจากบนลงล่างก็รู้ลำดับเหตุการณ์ทันที

ตำแหน่งในกระบวนการพัฒนา (จากเอกสาร)

  • Requirements Model: Requirements Elicitation → Functional/Nonfunctional Requirements → Use Case Diagrams / Sequence Diagrams (ระดับระบบ)
  • Object-Oriented Analysis: Static (Class Diagrams) · Dynamic (State Diagrams / Refined Sequence Diagrams — ระดับ object)

2. องค์ประกอบพื้นฐาน

องค์ประกอบคือจุดสังเกต
Actorผู้ใช้/ระบบภายนอกที่เริ่มปฏิสัมพันธ์อยู่นอกขอบเขตระบบ (outside the scope) เสมอ
Objectส่วนประกอบของระบบ (ถ้าเป็นโค้ด = Class)วางเรียงซ้าย→ขวาตามลำดับที่เข้ามาปฏิบัติการ
Lifelineเส้นประแสดงการมีชีวิตของ actor/object ตามเวลาเดินลงล่าง = เวลาผ่านไป
Messageข้อมูลที่ส่งระหว่าง object (ลูกศรแนวนอน)Request (เส้นทึบ, เปิดเรื่องใหม่) vs Return/Reply (เส้นประ, ตอบกลับ) — reply ไม่จำเป็นต้องวิ่งขวา→ซ้ายเสมอ
Activation boxแท่งบน lifeline แสดงช่วงที่ object ทำงานอยู่เห็นว่า object ไหนยุ่ง/ว่าง (เช่น Bank Account แทบไม่ active)

3. ชนิดของ Message (แบบละเอียด)

  • Self message — object เรียกตัวเอง
  • Recursive message — เรียกตัวเองโดยชี้ไปที่ activation ที่ซ้อนอยู่ด้านบน
  • Create message — สร้าง object ใหม่ (lifeline เริ่มต้นที่จุดนั้น)
  • Destroy message — ทำลาย lifeline ปลายทาง (มักมี X ปิดท้าย)
  • Duration message — แสดงระยะเวลาระหว่างจุดเวลา 2 จุดของการเรียก
  • Note — คอมเมนต์/หมายเหตุ ไม่มีผลเชิงความหมาย

4. Sequence Fragments (UML 2.0) — กล่องควบคุมการไหล

Fragment คือกล่อง (combined fragment) ที่ครอบส่วนของแผนภาพ มี operator มุมซ้ายบน บอกชนิด: ref, assert, loop, break, alt, opt, neg

alt — ทางเลือก

เลือกหนึ่งในหลายทาง (mutually exclusive) เช่น บัตรถูก/บัตรไม่ถูก — แบ่งด้วยเส้นประ (partition)

opt — ทางเลือกเดียว

ทำหรือไม่ทำ กรณีเดียว (เหมือน alt ที่มีทางเดียว) เช่น "ถ้าเงินไม่พอ → แจ้งเตือน"

loop — วนซ้ำ

ทำซ้ำตามเงื่อนไข เช่น loop [พินผิด < 3 ครั้ง]

5. ตัวอย่างเต็ม: ATM ถอนเงิน (สอนในเอกสารทีละขั้น)

📋 ลำดับเหตุการณ์ทั้งหมด (14 ขั้น)
  1. ลูกค้าใส่บัตรเข้าเครื่อง ATM
  2. ATM ตรวจบัตรกับ Bank Server ว่าบัตรใช้ได้ไหม
  3. Server ตรวจแล้วตอบกลับ ATM
  4. บัตรถูก → ATM ขอ PIN · บัตรไม่ถูก → คายบัตร (alt)
  5. ลูกค้ากรอก PIN (message นี้เป็น Return เพราะตอบคำขอของ ATM)
  6. ATM ถาม Server ว่า PIN ถูกไหม → Server ตอบ
  7. PIN ถูก → ATM ถามจำนวนเงิน · ไม่ถูก → คายบัตร
  8. ลูกค้ากรอกจำนวนเงิน
  9. ATM เริ่มธุรกรรมกับ Server
  10. Server ถามบัญชี (Bank Account) ว่าเงินพอไหม
  11. เงินพอ → Server ตัดยอดและสั่ง ATM จ่ายเงิน · ไม่พอ → ธุรกรรมไม่สำเร็จ
  12. บัตรถูกระงับ หรือ ธุรกรรมถูกยกเลิก → คายบัตร

ข้อสังเกตจากเอกสาร: object "Bank Account" มี activation น้อยมาก (ถูกถามแค่ครั้งเดียว) — activation box ช่วยให้เห็นภาพนี้

6. ทำไมต้องวาด ทั้งที่ใกล้โค้ดมาก? (Model before code)

  • Sequence diagram ที่ดียังอยู่เหนือระดับโค้ดจริงเล็กน้อย
  • Language neutral — ไม่ผูกกับภาษาโปรแกรมใด
  • คนไม่ใช่โปรแกรมเมอร์ก็วาดได้ (นักธุรกิจ/BA)
  • ทำเป็นทีมง่ายกว่าเขียนโค้ด
  • ใช้ต่อได้กับ testing และ UX wireframing
🎯 จุดที่ออกสอบ (แนวถูก/ผิด + เลือกตอบ)
  • เวลาใน sequence diagram ไหลบน→ล่าง (ไม่ใช่ซ้าย→ขวา)
  • Actor อยู่นอกขอบเขตระบบเสมอ
  • Return/Reply = เส้นประ · Request = เส้นทึบ · Reply ไม่จำเป็นต้องวิ่งขวา→ซ้าย
  • Fragment operator ยอดฮิต: alt (ทางเลือก), opt (หนึ่งเงื่อนไข), loop (วนซ้ำ)
  • ถ้าวาดโค้ด: object = ชื่อ Class · message = method/function

สรุปท้ายบท

✅ ต้องจำให้ได้จากบทนี้
  1. Sequence diagram = interaction diagram แสดงลำดับปฏิสัมพันธ์ object ตามเวลา (event diagrams/scenarios)
  2. องค์ประกอบ: Actor (นอกระบบ) · Objects · Lifeline · Message (Request ทึบ / Reply ประ) · Activation box
  3. Message ชนิดพิเศษ: self, recursive, create, destroy, duration + note
  4. Fragments: ref, assert, loop, break, alt, opt, neg
  5. ใช้จำลอง use case scenario → เป็นสะพานสู่การออกแบบ/ทดสอบ
🧪 ต้องการแสดง "ถ้า PIN ผิดให้ลูกค้ากรอกใหม่ แต่ไม่เกิน 3 ครั้ง" ควรใช้ fragment ใด?
💡 "ทำซ้ำตามเงื่อนไข (ไม่เกิน 3 ครั้ง)" = loop · opt ใช้กรณีทำหรือไม่ทำก็ได้ 1 เงื่อนไข · ref = อ้างแผนภาพอื่น · assert = ยืนยันว่าต้องเป็นไปตามนี้
