บทที่ 17 · Writing Functional Requirements — SRS & EARS ⭐

FR คือสิ่งที่ระบบ "ต้องทำ" — บทนี้คือหัวใจของควิซ 11: การตั้งรหัส FR · ลักษณะข้อกำหนดที่ดี · EARS/Active voice · ความคลุมเครือ · Boundary values · Negative requirements

1. ภาพรวม: เอกสารตามลำดับชั้น Requirements

  • Vision & Scope document เก็บ Business Requirements (บท 13)
  • User requirements เก็บเป็น use cases / user stories (บท 15-16)
  • FR + NFR เก็บใน SRS (Software Requirements Specification) — ส่งให้คนออกแบบ สร้าง และตรวจสอบทางออก
📖 SRS ตามมาตรฐาน ISO/IEC/IEEE 2011

ระบุ ฟังก์ชัน/ความสามารถที่ระบบต้องมี + คุณลักษณะ + ข้อจำกัด · บรรยายพฤติกรรมของระบบในสภาวะต่าง ๆ ให้ครบตามจำเป็น + คุณภาพที่ต้องการ (performance, security, usability) · เป็นฐานของการวางแผน ออกแบบ เขียนโค้ด ทดสอบ และคู่มือผู้ใช้ · ไม่รวม design/construction/testing/project management details (ยกเว้น design constraints ที่รู้แล้ว)

ใครใช้ SRS: ลูกค้า/การตลาด (รู้ว่าจะได้อะไร) · PM (ประมาณงาน) · ทีมพัฒนา (รู้ว่าต้องสร้างอะไร) · ผู้ทดสอบ (ทำ requirements-based tests) · ฝ่ายดูแล · ผู้เขียนคู่มือ · ฝ่ายกฎหมาย · ผู้รับเหมา (ผูกพันทางกฎหมายได้)

ลักษณะของชุด requirements ที่ดี (Collections) 4 ข้อ

  1. Complete — ไม่มีข้อ/ข้อมูลจำเป็นหาย (ข้อที่หายมองไม่เห็นเพราะมันไม่อยู่ตรงนั้น!)
  2. Consistent — ไม่ขัดแย้งกันเอง/กับ requirements ระดับบน
  3. Modifiable — มีประวัติการแก้ไขต่อข้อ + รู้ความเชื่อมโยงเพื่อแก้พร้อมกัน
  4. Traceable — ย้อนหลังถึงที่มา + ไปหน้าถึง design/โค้ด/แบบทดสอบ

3. EARS — Easy Approach to Requirements Syntax

📖 2 มุมมองการเขียน

System perspective: "The system shall…" / "must" / "needs to" + กริยา + ผลที่มองเห็น — และระบุ trigger/เงื่อนไข/event ที่ทำให้ระบบทำพฤติกรรมนั้น · ตัวอย่าง: "ถ้าสารเคมีที่ขอถูกพบในคลัง ระบบจะแสดงรายการภาชนะทั้งหมดของสารนั้น"

User perspective: "The [user class] shall be able to [do something] [to object] [qualifying conditions]" · หรือ "The system shall let/allow/permit/enable [user class] to [do something]" · ตัวอย่าง: "The Chemist shall be able to reorder any chemical he has ordered in the past by retrieving and editing the order details"

4. Active Voice — ประโยคาถูกต้องต้อง "รู้ว่าใครทำ"

❌ Passive (คลุมเครือ)✅ Active (ชัดเจน)
"ข้อมูลเครดิตบูโรจะได้รับการอัปเดต และผลการพิจารณาจะถูกส่งออก" (ใครทำ? ระบบ? ผู้ใช้?)"เมื่อผู้กู้กดยืนยัน ระบบจะตรวจสอบเครดิตบูโรผ่าน API ภายใน 5 วินาที"
"Serial number will be updated" (ใครอัปเดต?)"ระบบจะอัปเดต serial number ทุกครั้งที่บันทึกการขาย"
"ผู้ใช้ควรทำรายการได้อย่างราบรื่น ไร้รอยต่อ เป็นมิตร""หากยอดขอสินเชื่อ > 100,000 บาท ระบบจะแสดงหน้าจอให้อัปโหลดสลิปเงินเดือน 6 เดือน"

5. Writing Styles 5 ข้อ

  1. Punch line ก่อน — ข้อกำหนดนำหน้า, รายละเอียด (เหตุผล/ที่มา/priority) ตามหลัง
  2. ใช้ตาราง/ลิสต์/ไดอะแกรม ปน — ช่วยคนที่เรียนรู้ต่างสไตล์
  3. อย่าผสม passive กับ active ในเนื้อเดียวกัน
  4. ห้ามใช้หลายคำเรียกของเดียวกัน เพื่อความหลากหลาย (customer/account/patron/user/client = สับสน — เลือกคำเดียว)
  5. อ่านง่ายสำคัญกว่าน่าสนใจ

6. หลีกเลี่ยงความคลุมเครือ (Ambiguity) — ข้อสอบหลัก!

1) คำวัดไม่ได้ / กริยาวิเศษณ์

ห้าม: reasonably, appropriately, generally, approximately, usually, quickly, รวดเร็ว, เหมาะสม, ง่าย → แทนด้วยตัวเลขวัดได้: "ประมวลผลเสร็จภายใน 3 วินาทีในสภาวะโหลดปกติ"

2) คำเชื่อมรวมหลายข้อ

"และ / หรือ / additionally / also / unless / except / but" อาจแฝงหลาย requirements ในประโยคเดียว → แตกออกเป็นข้อ ๆ ที่ทดสอบแยกได้ · ห้ามใช้ "และ/หรือ" (and/or) เด็ดขาด — เช่น "ส่งแจ้งเตือนถึงลูกค้า/พนักงาน" ต้องระบุว่าลูกค้า หรือพนักงาน หรือทั้งคู่ ในสภาวะใด

3) A/B construct

"Delivery/Fulfillment Team" ตีความได้ 5 แบบ (ชื่อทีม? คำพ้อง? หรือ? และ?) → เขียนให้ชัดว่าหมายถึงอะไร

4) Boundary values (ค่าขอบเขต) ⭐

"<500 ไม่มีพอยต์ · 500-1,000 ได้ 50 · ≥1,000 ได้ 150" → 500 พอดี กับ 1,000 พอดี อยู่กลุ่มไหน? แล้ว 500.50 ล่ะ? → ใช้คำชัดเจน: "5 วันหรือน้อยกว่า (5 or fewer)" · "ยาวกว่า 5 วันถึง (through) 10 วัน" · "ยาวกว่า 10 วัน" — through/inclusive/exclusive คือคำมหัศจรรย์

Negative Requirements → เปลี่ยนเป็นบวก

"ระบบจะต้องไม่ยอมให้พนักงานทั่วไปเข้าถึงรายงานเงินเดือน" — จะ implement "อย่า ๆ ไหน"? ทดสอบยังไง? → เขียนใหม่เป็นพฤติกรรมบวกที่ระบุสิทธิ์: "ระบบจะอนุญาตเฉพาะผู้ใช้กลุ่ม Department Manager ให้เรียกดูรายงานเงินเดือนประจำแผนก (พร้อมแจ้งเตือน/บันทึกการพยายามเข้าถึง)" · ปฏิเสธซ้ำชั้น ("ต้องไม่ปฏิเสธผู้ที่ไม่ได้ไม่มีตำแหน่ง…") ห้ามเด็ดขาด

ระดับความละเอียด (Level of Detail)

ควรละเอียดมากเมื่อ…ควรละเอียดน้อยลงได้เมื่อ…
· งานให้ลูกค้าภายนอก
· Outsource พัฒนา/ทดสอบ
· ทีมกระจายพื้นที่ (geographically dispersed)
· ทดสอบยึดตาม requirements (requirements-based testing)
· ต้องการประมาณงานแม่น
· ต้องการ traceability		· งานภายในบริษัทเอง
· ลูกค้ามีส่วนร่วมตลอด
· นักพัฒนาชำนาญ domain สูง
· มีงานเดิมเป็นตัวอย่าง (replace ระบบเก่า)
· ใช้ซอฟต์แวร์สำเร็จรูป (package) มาปรับแต่ง

Granularity ที่ดี: เขียนให้ individually testable — ถ้าคิด test cases ที่สัมพันธ์กัน "จำนวนน้อย" ได้ = ขนาดพอดี · ถ้าต้องใช้ tests มากมายหลายแนว = หลาย requirements รวมกันอยู่ ให้แยก · ไม่จำเป็นต้องละเอียดเท่ากันทุกข้อ แต่พยายามให้สม่ำเสมอ
