บทที่ 14 · Finding the Voice of the User — User Classes, Personas, Product Champion

ความสำเร็จของ requirements ขึ้นกับการนำ "เสียงผู้ใช้" ไปใกล้ "หูนักพัฒนา" (⭐ ควิซ 10 ออกเกือบทั้งชุด)

1. หลักคิดเปิดบท

📖 Voice of the User

"ความสำเร็จของ software requirements (และการพัฒนาซอฟต์แวร์) ขึ้นกับการนำ เสียงของผู้ใช้ไปใกล้หูของนักพัฒนา" — ขั้นตอน: ① ระบุ user classes ต่าง ๆ ② เลือกและทำงานกับผู้แทนของแต่ละ class ③ ตกลงว่าใครคือ requirements decision makers

🔑 การมีส่วนร่วมของลูกค้า (customer involvement) คือวิธีดีที่สุดที่จะหลีกเลี่ยง expectation gap — และ "wants" ที่ผู้ใช้เสนอไม่จำเป็นต้องเท่ากับ "needs" ที่ใช้ทำงานจริง: BA ต้องรวบรวม input หลากหลาย → วิเคราะห์/ทำให้ชัด → ระบุเฉพาะสิ่งที่ต้องสร้าง · ถ้าไม่ลงทุนทำเรื่องนี้ → rework + ส่งช้า + งบเกิน + ลูกค้าไม่พอใจ

💭 เจ้าหน้าที่คลังกับปุ่มสีแดงกะพริบ (ตัวอย่างควิซจริง)

ผู้จัดการคลัง: "อยากได้ปุ่มสีแดงกะพริบหน้าแรก คลิกดูรายงานยอดคงเหลือ" — BA ที่ดีไม่จดเป็น FR ทันที แต่มองว่านี่คือ want → ถามต่อ: งานจริง (task) ที่เขาต้องการทำให้สำเร็จคืออะไร? (ดูรายงานประจำวัน) → แล้วค่อยออกแบบทางเข้าถึงรายงานที่ดีกว่าปุ่มกะพริบร่วมกับทีม — แก้โจทย์ ไม่ใช่แก้คำขอ

2. User Classes — จัดกลุ่มผู้ใช้

  • User class = ส่วนย่อยของ "ผู้ใช้" ของผลิตภัณฑ์ (ผู้ใช้ ⊂ ลูกค้า ⊂ stakeholders) · คนหนึ่งอยู่ได้หลาย class · user class ไม่จำเป็นต้องเป็นมนุษย์ (software agents/bots ที่ทำงานแทนคนก็นับ)
  • วิธีคิดที่ดีกว่าดู "ตำแหน่ง": คิดจาก งาน (tasks) ที่กลุ่มต่าง ๆ จะทำกับระบบ
🎯 จุดสอบของ User Classes
  • เกณฑ์ตัดสิน Favored = ความสอดคล้องกับ business objectives ไม่ใช่ "คนจ่ายเงิน" หรือ "อำนาจทางการเมือง"
  • Disfavored: สร้าง feature ที่จงใจทำให้ยาก เช่น lock account หลังพินผิด 4 ครั้ง, ขอ OTP ถ้าเครื่องไม่รู้จัก
  • Ignored ≠ Disfavored: Ignored ใช้ได้แต่ไม่ออกแบบให้ (ไม่ได้บล็อก!)
  • แยก class ตาม: สิทธิ์การเข้าถึง · งานที่ทำ · ฟีเจอร์ที่ใช้ · ความถี่ใช้ · ประสบการณ์ domain/IT · platform · ภาษา · ติดต่อตรง/อ้อม

วิธีระบุ User Classes — "Expand then Contract"

  1. ถาม project sponsor ว่าคาดว่าใครใช้ระบบ
  2. ระดมสมองให้มากที่สุด (หลายสิบกลุ่มก็ไม่ต้องตกใจ)
  3. รวมกลุ่มที่ความต้องการคล้ายกัน (หรือเป็น class ใหญ่ + subclasses)
  4. บีบให้เหลือ ≤ 15 กลุ่ม — อย่าลืมกลุ่มใดไป เดี๋ยวช้า ๆ มาคนเดือนว่าระบบไม่ตอบโจทย์!

Organization chart analysis: ดูแผนผังองค์กรเพื่อหา: แผนกที่มีส่วนร่วม/ได้รับผลกระทบจากกระบวนการ · จุดที่ซ่อน direct/indirect users · user class ที่คร่อมหลายแผนก · แผนกที่เชื่อมต่อ stakeholder ภายนอก (+ เข้าใจว่าแต่ละแผนก "ให้ข้อมูลอะไร" ตามบทบาท-มุมมองของเขา)

⚠️ กับดัก focus group: อย่าเลือกแต่ early adopters / blue-sky thinkers — จะได้แต่ requirements หรูหรายากที่ลูกค้าจริงไม่ใช้ · ต้องมีทั้งผู้ใช้เก่งและมือใหม่

3. User Personas

📖 นิยาม

Persona = คำอธิบายของบุคคลสมมติ (hypothetical generic person) ที่เป็นตัวแทนกลุ่มผู้ใช้ที่มีลักษณะ-ความต้องการคล้ายกัน — ใช้เข้าใจ requirements และออกแบบ user experience · เป็น placeholder เมื่อไม่มีตัวแทนผู้ใช้จริง · ต้องสร้างจากการวิจัยตลาด/ประชากร/ชาติพันธุ์วิทยาจริง (❌ ตั้งชื่อ+วาดรูปเฉย ๆ ใช้ไม่ได้)

4. Product Champion

📖 หลักการ

โครงการต้องมีผู้แทนผู้ใช้ที่เหมาะสม และต้องมีส่วนร่วมตลอด life cycle ไม่ใช่แค่ช่วง requirements · ทุก user class ต้องมีคนพูดแทน · พิจารณาตั้ง focus groups (ของลูกค้าจริง/ของคู่แข่ง) — ถามจริง ดีกว่าเดา

  • Product Champion คือใคร: ผู้ใช้จริง (ไม่ใช่ sponsor/ผู้จัดการที่ไม่ได้ใช้ระบบ) · หน้าที่: รวบรวมความต้องการจากเพื่อนร่วมงานใน class ตน + ช่วยไกล่เกลี่ยข้อขัดแย้ง · ต้องได้รับอำนาจเต็มที่ในการตัดสินใจแทนกลุ่ม (หนึ่ง class หนึ่ง champion — ไม่ใช่คนเดียวทำแทนทุก class)
  • แบ่งเบาความกังวลผู้บริหาร: champion ตัดสินใจเฉพาะระดับ user requirements ภายใต้กรอบ business requirements · ผู้บริหาร (sponsor) ยังถืออำนาจเรื่อง product vision, scope, priorities เชิงธุรกิจ, schedule, budget · ต้องเขียนบทบาท-หน้าที่ให้ชัด
  • เมื่อเจอ resistance: ย้ำว่า "การขาด user involvement เป็นสาเหตุอันดับต้น ๆ ของโครงการล้มเหลว" + ยกตัวอย่างหนัง ๆ จากอดีต (นรกที่เคยเจอ) — champion ช่วยให้ได้ customer input ทันเวลา ไม่ใช่ปลายโครงการ
⚠️ Product Champion Traps (ออกสอบ!)
  1. ผู้บริหารล้มการตัดสินของ champion ตลอด → ผู้ใช้ไม่พอใจ champion รู้สึกไม่ได้รับความไว้วางใจ
  2. Champion นำเสนอแต่ความต้องการตัวเอง ลืมว่าต้องเป็นตัวแทนลูกค้าคนอื่น
  3. Champion ไม่มีวิสัยทัศน์ → ยอมทุกอย่างที่ BA เสนอ (defer การตัดสินใจทั้งหมด) = ไม่ได้ช่วยอะไร
  4. รุ่นพี่โยนงานให้น้องใหม่ไม่มีประสบการณ์ + ยังคอย "ขับรถย้อนหลัง" (backseat driving) อยู่
  5. ระวังคนที่อ้างว่าพูดแทน class ที่ตนไม่ได้อยู่

5. บน Agile: Product Owner

  • Agile มี Product Owner คนเดียวเป็นเสียงของลูกค้า: นิยาม product vision + จัดลำดับ product backlog (รายการ user stories เรียงตาม priority + จัดสรรเข้า sprints ของ Scrum)
  • Product owner ครอบคลุม ทั้ง 3 ระดับ requirements (business, user, functional) — "นั่งข้าม" บทบาท product champion + BA
  • คนเดียวอาจไม่พอในองค์กรใหญ่: บริษัทประกัน (แพ็กเกจระบบ) ใหญ่และซับซ้อนเกินกว่าใครคนเดียวจะรู้ครบ → เลือก product owner หนึ่งคนต่อแผนก เป็นเจ้าของ priority ของฟังก์ชันแผนกตน
  • Product Owner กับ Product Champion ใช้ร่วมกันได้ (ไม่เห็นแย่งกัน): ถ้า PO ทำหน้าที่แบบ BA ก็ตั้ง champions เป็นแหล่ง input ได้ · หรือ PO ทำงานกับ BA หลายคน — PO เป็น decision maker สุดท้าย

สรุปท้ายบท

✅ ต้องจำให้ได้
  1. Wants ≠ Needs — BA ต้องวิเคราะห์ให้ถึง "task ที่ผู้ใช้ต้องทำให้สำเร็จ"
  2. User class: คนหนึ่งได้หลาย class · ไม่จำเป็นเป็นมนุษย์ · คิดจาก tasks · Expand-then-Contract ≤15 กลุ่ม
  3. 4 กลุ่ม: Favored (ตาม objectives!) · Disfavored (กันโดยเจตนา) · Ignored (ไม่ออกแบบให้) · Other
  4. Persona = ตัวแทนสมมติที่ตั้งบนข้อมูลวิจัยจริง
  5. Product Champion = ผู้ใช้จริง+อำนาจตัดสิน+เก็บเสียงทั้งกลุ่ม · กับดัก 4-5 ข้อ · ผู้บริหารยังคงอำนาจ vision/scope/งบ
  6. Product Owner (Agile) = 1 คน/แผนก ได้ · ใช้ร่วมกับ champion ได้
🧪 (ควิซจริง) เกิดข้อขัดแย้งความต้องการระหว่างลูกค้าทั่วไปกับผู้ดูแลระบบส่วนกลาง — ควรตัดสินอย่างไร?
