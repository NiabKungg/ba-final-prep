บทที่ 18 · Non-Functional Requirements (NFR)

NFR = Constraints — ข้อจำกัดที่การออกแบบ/สร้างต้องเคารพ · จัด 3 หมวดใหญ่ + คุณภาพ + Supplementary Specifications + การ trade-off

1. FR vs NFR — เส้นแบ่งที่ต้องชัด

Functional RequirementsNon-Functional Requirements
ระบบทำอะไร (what the system should do)ประกอบด้วย Constraints ที่ต้องเคารพระหว่างพัฒนา (design + implementation) — คำสำคัญคือ "Constraints"
input ที่รับ · output ที่ผลิต · ข้อมูลที่เก็บให้ระบบอื่นใช้ · การคำนวณ · timing/synchronization ของสิ่งเหล่านี้มักไม่ผูกกับ use case เดียว — แทรก穿透ตัว (transcend locality) หลาย use cases · บางตัวขัดกันเอง (เร็ว vs ดูแลง่าย)
🎯 เกณฑ์ตัดสินว่าเป็น FR หรือ NFR (Random Thoughts จากเอกสาร)
  • ถ้าข้อกำหนดนั้นเป็นส่วนหนึ่งของหน้าที่หลักของแอป → เขียนเป็น FR (เช่น performance ของระบบ real-time, reliability ของระบบ safety-critical!)
  • ถ้าเป็นข้อจำกัด/การจำกัดการออกแบบ → เป็น NFR เกือบทั้งหมด
  • NFR ทุกข้อต้อง verifiable (ตรวจได้) และบางข้อต้อง measured (วัดค่าได้/วัดผ่าน simulation)

2. 3 หมวดใหญ่ของ NFR

3. Quality Models — โมเดลคุณภาพหลายสำนัก

  • Product Operation: Accuracy, Reliability, Efficiency, Integrity, Usability · Product Revision: Maintainability, Flexibility, Testability · Product Transition: Interface facility, Reusability, Transferability
  • Barry Boehm: Validity, clarity, understandability, modifiability, modularity, generality, economy, resilience, documentation
  • Laurence Best: Accuracy & comprehensiveness · simplicity of use · operational flexibility · ease of development/maintenance/extension · security & control · resource efficiency · recovery
  • แนวคิด: มีหลายรายการ "คุณภาพ" — แต่ละ attribute ต้องถูกพิจารณาตอนออกแบบ (architect ต้องวนหลายรอบ: เริ่มจาก functionality → ค่อยใส่ modifiability โดยไม่ทำฟังก์ชันพัง)

Trade-offs — ทุกอย่างแลกกันหมด

  • Performance มักใช้ fewer indirection + optimize โครงสร้าง → ลด maintainability/reusability
  • Cost ขัดกับทุกอย่าง — และ "usability มักถูกเสียสละเป็นอันดับแรก!"
  • Architect ต้องหาดีไซน์ที่สมดุลระหว่าง NFR ที่แข่งกัน · อย่าให้ assumption ของ user พาไปสู่ "architectural nightmare" (เช่น ต้องการ availability 100%)

4. เก็บ NFR ไว้ที่ไหน — Use Case vs Supplementary Specifications

  • ใน RUP NFR อยู่ใน Supplementary Specifications (ห้ามคิดว่า "supplementary" = รอง — เยอะแยะโครงการพังเพราะละเลยมัน: เคส "รองรับ 300-500 ผู้ใช้พร้อมกัน" แต่ตอน UAT รับได้แค่ 8 — ทีมหมกมุ่น UI จนระบบไม่เคยถูก deploy!)
  • เก็บใน use case เมื่อ NFR ใช้เฉพาะบริบท use case นั้น · เก็บใน Supplementary Specs เมื่อเป็น global/ไม่เปลี่ยนตาม use case — ถ้า interaction เยอะ ส่วนใหญ่เก็บใน use case · ถ้า interaction น้อย ส่วนใหญ่เป็น NFR · รักษาสมดุล ต้องมีทั้งคู่
  • หมวดตาม Bittner & Spence: Legal & Regulatory (อายุถึงกฎหมายจึงซื้อแอลกอฮอล์ได้) · Application Development Standards (พัฒนาตาม RUP) · Quality attributes (available ≥ 90%) · Constraints (เขียนด้วย Java 2) · Others

กระบวนการจัดการ NFR (Kulak & Guiney)

  1. Identify — ถาม user เรื่อง response time/สิ่งที่รำคาญตอนนี้
  2. Validate กับ stakeholder ที่เกี่ยวข้อง
  3. Document — ชื่อ + ผลกระทบ (ถ้าไม่สำเร็จ ระบบ/ธุรกิจเสียหายอย่างไร) · จับทันทีที่ถาม (interview/questionnaire) · แยก "ความกังวลธุรกิจ" (ใส่ use case) ออกจาก NFR
  4. Rank — สำคัญมาก! บาง NFR แพงกว่าตัว use case เอง · ไม่มีของฟรี
  5. ใช้ตารางเทมเพลต: Category · Number · Name · Description · Applies to Use Case(s) · Exceptions (+priority ได้)

✅ ต้องจำให้ได้
  1. NFR = Constraints (คำเดียวที่ต้องจำ) · FR = สิ่งที่ระบบทำ
  2. 3 หมวด: Quality (response/throughput/resource/MTBF/availability/MTTR/reusability) · Environment & Tech (platform/ภาษา) · Project Plan & Methods (process/งบ-กำหนดส่ง)
  3. ถ้าเป็นหน้าที่หลักของแอป = FR แม้จะฟังดู "ด้านคุณภาพ" (real-time/safety-critical)
  4. NFR ต้อง verifiable (+measured) · ต้อง rank (บางตัวแพงกว่า use case)
  5. เก็บ global NFR ใน Supplementary Specs · เฉพาะ use case ใส่ใน use case · ต้องสมดุลทั้งคู่
  6. Trade-offs: performance↔maintainability · cost↔ทุกอย่าง · usability โดนเสียสละบ่อยสุด
