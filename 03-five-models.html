บทที่ 3 · 5 Aspects of Business Models

ธุรกิจเดียวกันสามารถ "ถูกมอง" ได้ 5 มุม — แต่ละมุมตอบคำถามต่างกัน (Who / What / When / Where / How) และมีโมเดลประจำมุม นี่คือเนื้อหาที่ออกสอบควิซแน่นอน (ควิซ 9 ตั้งแต่ข้อ 1 ถึงข้อ 11!)

💭 นึกภาพก่อนเรียน

ลองนึกถึง ร้านสะดวกซื้อ 1 สาขา: มุมมองเดียวดูไม่ครบ — ต้องถามครบ 5 คำถาม: ทำงานอย่างไร (พนักงานคิดเงินอย่างไร = Process) · มีอะไร (สินค้า/คำสั่งซื้อ = Data) · เมื่อไร (สถานะคำสั่งซื้อเปลี่ยนเมื่อไหร่ = Event) · ที่ไหน (สาขา/คลัง/เส้นทาง = Location) · ใคร (พนักงาน/แผนก/ผู้จัดส่ง = Socio-Political) — อาจารย์วาดเป็นวงกลมเพราะทั้ง 5 มุมคือ "สิ่งเดียวกัน" ที่มองจากต่างมุม!

  • ❌ "Business Event Model เน้น Where" — ผิด! Event = When, Location = Where

  • ✅ สถานะ "สินค้าอยู่ระหว่างตรวจสอบคุณภาพ" = Node ของ Business Event Model (State)
  • ✅ "สาขาจตุจักร" = Node ของ Location Model ไม่ใช่ Process Model

2. Business Process Model (How?)

  • จุดมุ่งหมาย: แทน Business work requirements — "เราทำงานนี้อย่างไร" (เช่น เติมออเดอร์อย่างไร จ้างคนอย่างไร) เป็นรากฐานให้ Application procedural designs → โค้ด และ Manual procedure designs → คู่มือปฏิบัติงาน
  • Nodes = Activities · Links มีได้หลายแบบ:
    • Control — ลำดับการทำงาน (ใครทำก่อน-หลัง)
    • Data/material dependencies — input/output ของงาน
    • Performer — ใครทำ (มักแสดงด้วย swim lanes)
    • Interface — ใคร/อะไรให้-รับ input/output
    • Hierarchy — งานใหญ่ม้วนขึ้น (roll-up) / แตกลง (break-down) อย่างไร
  • Process Map vs DFD: Process Map เน้น Links = Control + Performer (swimlanes) · DFD เน้น Links = Data & material dependencies + Interfaces
  • กริยาต้นแบบของกิจกรรม: Receive/Get · Review/Verify · Determine/Calculate · Produce/Develop/Create · Conduct/Monitor · Assign · Prioritize · Deliver/Issue/Send
  • ตัวอย่างจากเอกสาร: การขอใบอนุญาตก่อสร้าง — Receive Application (Receptionist) → Review for Completeness (Permit Clerk) → Review for Compliance (Inspector) → Issue Permit (Permit Clerk)

3. Business Object/Data Model (What?)

  • จุดมุ่งหมาย: แทน (1) แนวคิด/คำศัพท์ของสิ่งของในธุรกิจ ("สินค้า" คืออะไร? "คำสั่งซื้อ" คืออะไร?) และ (2) ความต้องการข้อมูล (เราต้องรู้อะไรเกี่ยวกับมัน?) — เป็นรากฐานของ Data store designs
  • Nodes = Entities ตัวอย่าง: สินค้า คำสั่งซื้อ ลูกค้า ยานพาหนะ เอกสาร โรค เฟอร์นิเจอร์ · Links = Relationships เช่น contains / classifies / is assigned to / is affiliated with / employs / purchases / is prerequisite for
  • Attributes = ส่วนเสริมที่บอกว่าต่อ entity หนึ่งเราเก็บข้อมูลอะไร (เช่น รถ 1 คัน มี make, model, VIN)
🎯 เกณฑ์ตัดสิน "สิ่งนี้ควรอยู่ใน Data Model ไหม?"

ใส่ใน Data Model เมื่อ ต้อง "track" — มี information requirement (ต้องเก็บข้อมูลอะไรต่อสิ่งนั้น) หรือต้องนิยามคำศัพท์ให้ชัด

แต่ถ้าแค่ต้อง "do" มัน → ไป Process Model · ต้อง "be there" → Location Model · ต้อง "serve" → Socio-Political Model · ต้อง "respond" → Event Model

4. Business Event Model (When?)

  • จุดมุ่งหมาย: แทน Business timing requirements — ธุรกิจต้องตอบสนองเหตุการณ์ภายนอกอะไร? และเหตุการณ์เปลี่ยนสถานะ (status) ของสิ่งใด? เป็นรากฐานของ trigger designs และ status tracking
  • Nodes = States (ของ entity/relationship) · Links = Events (เหตุการณ์ที่ทำให้เปลี่ยนสถานะ)

5. Business Location Model (Where?)

  • จุดมุ่งหมาย: แทน Business location requirements — ต้องดำเนินธุรกิจที่ใด? อะไรต้องเดินทางข้ามสถานที่? — เป็นรากฐานของ Facility designs + Network designs
  • Nodes = Locations/Sites: แบ่งตามเจ้าของ (Internal/External) และธรรมชาติ (Geographic areas = เน้นขอบเขต / Sites = เน้นจุด ระบุที่อยู่ได้) เช่น Office, Store, Plant, Warehouse, Lab, Building, รถ (mobile site), "any connected site"
  • Links = Channels 4 ชนิด:
    1. Data — ข้อมูลวิ่งระหว่างสถานที่
    2. Control — สัญญาณ trigger ("OK ที่จะเริ่มงาน")
    3. Material — ของจริง/เอกสารต้นฉบับที่ต้องขนส่ง
    4. Participants — คนเคลื่อนย้าย (พนักงาน/ลูกค้า)
  • สิ่งที่เดินทางผ่าน channel (Cargo) อาจเป็น ข้อมูล / สินค้า / คน ได้ทั้งหมด

6. Business Socio-Political Model (Who?)

  • จุดมุ่งหมาย: แทน Business organizational requirements — ต้องรองรับองค์กรภายนอก/กลุ่มสังคมใด? โครงสร้างองค์กรแบบไหนสนับสนุนเป้าหมาย? ต้องการ roles อะไร? — เป็นรากฐานของ Organization designs + External interface requirements
  • 2 แบบไดอะแกรม:
    • Party Affiliation Diagram — Nodes = Parties (คน/องค์กร) · Links = Affiliations
    • Org Chart — Nodes = Org Units · Links = สายบังคับบัญชา + เส้นประ functional accountability
  • Affiliations ที่พบบ่อย: Customer (current/potential) · Vendor (current/preferred/potential) · Org Parent–Org Child (บริษัทแม่-ลูก) · Partner (collaboration) · Competitor · Substitution
  • Roles 3 กลุ่ม: Performing (Coordinator, Analyst, Clerk…) · Leadership (Team lead, PM) · Management (Executive, Manager)
🧠 เครื่องมือเสริม: Role Profile Matrix (ออกสอบ!)

ตารางบันทึกคุณลักษณะของแต่ละ Role เพื่อออกแบบระบบให้เหมาะกับผู้ใช้จริง ประกอบด้วย:

  • Role Description — General description, Explicit authorities, Credentials, Other responsibilities
  • Population size (จำนวนคน) · Literacy (ความรู้ด้าน subject area + technical) · Language(s) · Tenure · Work period · Salary grade
  • Special accommodation needs — สายตา/สี/การได้ยิน/การเคลื่อนไหว
  • System usage — ชนิดการใช้ (Navigation, Inquiry, Data entry, Updates, Approvals, Reports) + ความถี่
  • Stand to Gain — สิ่งที่ได้ (automation งานน่าเบื่อ, เข้าถึงข้อมูลดีขึ้น, เครื่องมือดีขึ้น, audit trails)
  • Stand to Lose — สิ่งที่เสีย (อำนาจควบคุมบางฟังก์ชัน, ต้องเรียนใหม่, ความเชี่ยวชาญเดิม, งาน, "เครื่องจักรตัดสินใจแทนที่คน")

💡 ควิซ: "การจัดทำ Role Profile Matrix เพื่ออธิบายคุณลักษณะเฉพาะของแต่ละบทบาท เป็นเครื่องมือสนับสนุน Socio-Political Model" ✅ และ "Link ของโมเดลนี้ เช่น ร้านค้าเป็นผู้ให้บริการกับลูกค้า" ✅

7. Cross-Model — วิเคราะห์ข้ามโมเดล

  • โมเดลแต่ละชนิดคือ "สิ่งเดียวกันจากมุมต่างกัน" — สร้างหลายโมเดลร่วมกันช่วยให้ค้นพบปัญหาที่แท้จริงและหาทางออกได้ง่ายขึ้น
  • ทำ cross-reference ได้ 2 ทาง: (1) ฝังไว้ในโมเดลหลักเป็น annotation · (2) สร้าง cross-reference matrices (ทำเป็น formal specification หรือ sketch ก็ได้)
  • หลักการปิดท้ายจากผู้สอน: "Do whatever your needs dictate and your time allows" — ไม่จำเป็นต้อง cross-reference ครบ 100% ทุกโมเดลเสมอไป
  • ตัวอย่างเมทริกซ์: จับคู่ ข้อมูล × กระบวนการ (เช่น CRUD: กระบวนการใด สร้าง(C)/อ่าน(R)/แก้(U)/ลบ(D) ข้อมูลใด)
🎯 แบบฝึกจับคู่ (เหมือนในเอกสาร — ลองทำดู!)

สิ่งต่อไปนี้ควรอธิบายด้วยโมเดลใด? (เฉลยกดดู)

กดดูเฉลยพร้อมเหตุผล
  1. "ต้องรู้ว่าคนใดทำกิจกรรมใดเสร็จ" → Data Model (มี information requirement ต้อง track ความสัมพันธ์ คน-งาน)
  2. "รับ order → เช็ค stock → แพ็ค → ส่ง" → Process Model
  3. "คำถามลูกค้าทั้งหมดดูแลโดยตัวแทน CRM" → Socio-Political Model (role)
  4. "ฝ่ายขายมี 3 สายงานย่อย" → Socio-Political Model (org units)
  5. "ศูนย์ขายมี 4 ห้องขาย" → Location Model
  6. "เมื่อโจทก์ถอนคดี ถือว่า 'closed'" → Event Model (เปลี่ยน state)
  7. "เมื่อถอนคดี ต้องแจ้งทุกฝ่ายและยกเลิกการนัด" → Event + Process Model (event ทริกเกอร์งาน)
  8. "รถแต่ละคันมี make, model, VIN" → Data Model (attributes)

8. Case Study สุดคลาสสิก: Calvert County (การขอใบอนุญาตก่อสร้าง)

🏛️ ปัญหา As-Is → ทางแก้ด้วยแต่ละโมเดล

ปัญหาเดิม: ขั้นตอนรีวิวยาวเหยียดซับซ้อน ทุกอย่างเป็นกระดาษส่งต่อในแฟ้ม ไม่มีใครรู้สถานะคำขอ ผู้ขอได้คำแนะนำว่า "เตรียมสมุดเช็คและรองเท้าเดินสบาย ๆ มาด้วย"

  • Process: FIFO ทำให้งานเล็กก็ต้องรองานใหญ่ → แก้ด้วย triage 3 ระดับ (Simple ประเมินทันที / Routine จองเวลารีวิวพร้อมกัน / Complex ตามมาตรฐาน) + เปลี่ยน รีวิวเรียงลำดับเป็นขนาน (concurrent) เพราะ dependency จริงมีแค่จุดเดียว → เวลารวมลดมหาศาล
  • Event: สถานะคำขอบอกไม่ได้ → ระบุ+ติดตามสถานะแบบละเอียด (Submitted → Approved → Pending Payment → Issued → Expired) + ใช้ super state "UNDER REVIEW" ให้หลายกิจกรรมเริ่มพร้อมกัน
  • Socio-Political: ผู้ขอต้องคุยกับ 17 หน่วยงาน → สร้าง role "Permit Coordinator" เป็นคนกลาง (แม้มีข้อจำกัด "ห้ามตั้งตำแหน่งใหม่" แต่โมเดลช่วยพิสูจน์ว่าคุ้มค่า)
  • Location: ผู้ขอต้องเดินไล่หลายอาคาร → รวมจุดติดต่อไว้ที่เดียว (Building Permit Office) + เปลี่ยนช่องทางจากของจริง (กระดาษ) เป็นข้อมูลดิจิทัล ไม่ต้องขนแฟ้ม
  • Data: คำศัพท์ที่ดินสับสน (block/section/parcel/subdivision/lot) → นิยามชัด + ERD

ธีมสรุป: แต่ละโมเดลทำให้ เห็นปัญหา (discovery + communication) และ เห็นทางแก้ (assessment + specification + communication ต่อผู้บริหาร/vendor) — และทำได้ "เร็ว"

💭 อุปมา "ปริศนาและกุญแจ" (Puzzle & Key)

แต่ละ business need = ปริศนาหนึ่งข้อ ที่มีกุญแจของมันเอง · แต่ละโมเดล = กุญแจดอกหนึ่ง — บางปริศนามีหลายกุญแจ แต่มักมี "กุญแจที่หรูหราที่สุด" ดอกเดียว ที่: แก้ปัญหาจริง · ชัดเจน · เข้าใจง่าย · โต้แย้งยาก · ประหยัด · แก้ปัญหาแถมไปด้วย — เราเดาล่วงหน้าไม่ได้ว่าโมเดลไหนคือกุญแจ จึงควร sketch ทุกโมเดล "อย่างน้อยระดับหนึ่ง"

สรุปท้ายบท

✅ ต้องจำให้ได้จากบทนี้
  1. 5 คำถาม-5 โมเดล: Process=How · Data=What · Event=When · Location=Where · Socio-Political=Who
  2. Node/Link ของแต่ละโมเดล: Activities/Control · Entities/Relationships · States/Events · Sites/Channels · Parties/Affiliations
  3. Event 3 ประเภท: Time · Business · Natural / Channel 4 ประเภท: Data · Control · Material · Participants
  4. Role Profile Matrix เป็นเครื่องมือของ Socio-Political Model (Stand to Gain / Stand to Lose)
  5. โมเดล = สิ่งเดียวกันต่างมุม → ใช้ร่วมกัน + cross-reference matrices
  6. กรณี Calvert County: triage, concurrent review, Permit Coordinator, รวมสถานที่, ลำดับความสำคัญของสถานะ
