บทที่ 16 · Use Case Modeling (มุม UML)

บทนี้เพิ่มเติมเรื่อง Use Case จากมุมมอง System Analysis: ประโยชน์เต็ม ๆ · Actor 4 ชนิด · ความสัมพันธ์ include/extend/depends/inheritance · Use Case Narrative · Ranking Matrix · Misuse Case

"ส่วนที่ยากที่สุดของการสร้างระบบซอฟต์แวร์คือการตัดสินใจว่าจะสร้างอะไรกันแน่… ไม่มีงานไหนที่ทำพลาดแล้วบั่นทอนระบบได้มากไปกว่านี้ และไม่มีอะไรแก้ยากไปกว่านี้ในภายหลัง" — Fred Brooks

1. User-Centered Development & ประโยชน์ของ Use-Case Modeling

  • User-centered development = พัฒนาระบบโดยยึดความเข้าใจความต้องการของ stakeholder + เหตุผลที่ระบบควรถูกพัฒนา
  • Use-case modeling = สร้างโมเดลฟังก์ชันของระบบในรูป business events — ใครเริ่ม event และระบบตอบสนองอย่างไร

ประโยชน์ (จำเป็นชุด): เครื่องมือเก็บ functional requirements · ช่วยแตกระบบเป็นชิ้นที่บริหารได้ · สื่อสารกับผู้ใช้ด้วยภาษาที่เขาเข้าใจ · ระบุ-มอบหมาย-ติดตาม-ควบคุมงานพัฒนา · ช่วยประเมิน scope/effort/schedule · กำหนดแผน-กรณีทดสอบ · เป็นฐานคู่มือผู้ใช้ · requirements traceability · จุดเริ่มหา data objects/entities · ข้อกำหนดออกแบบ UI/การเข้าถึงฐานข้อมูล · กรอบขับเคลื่อนโครงการทั้งหมด

2. นิยามหลัก 3 ตัว

ตัวคือ
Use caseลำดับขั้นตอนที่สัมพันธ์กันเชิงพฤติกรรม (scenario) — อัตโนมัติ+มือ — เพื่อเสร็จสิ้นงานธุรกิจหนึ่ง ๆ · อธิบายฟังก์ชันจากมุมผู้ใช้ภายนอก
Use-case diagramภาพแสดงปฏิสัมพันธ์ระหว่างระบบ กับ ระบบภายนอก/ผู้ใช้ — ใครใช้อย่างไร
Use-case narrativeข้อความบรรยาย business event + ผู้ใช้โต้ตอบกับระบบอย่างไรเพื่อเสร็จงาน

Actor 4 ชนิด (ออกสอบ!)

👤 Primary business actor

ผู้ที่ได้ประโยชน์หลักจากการใช้ use case — เช่น พนักงานที่ได้รับเงินเดือน

⌨️ Primary system actor

ผู้ที่ติดต่อระบบโดยตรงเพื่อเริ่ม/ทริกเกอร์ event — เช่น พนักงานธนาคารคีย์รายการฝาก

🤝 External server actor

ผู้ที่ตอบสนองคำขอของ use case — เช่น บริษัทเครดิตที่อนุมัติการชาร์จบัตร

📦 External receiver actor

ผู้ที่ไม่ใช่ primary แต่ได้รับบางอย่างที่มีคุณค่า — เช่น คลังสินค้าที่รับใบแพ็คสินค้า

⚠️ Temporal event — เหตุการณ์ที่ระบบทำงานเมื่อถึงเวลา (เช่น รายงานรายสัปดาห์) → actor คือ "Time"

3. ความสัมพันธ์ใน Use Case Diagram

ความสัมพันธ์คืออะไรทิศลูกศร
Associationการโต้ตอบ actor–use case · มีหัวลูกศร = เริ่มโดย actor · ไม่มีหัว = receiver actor · เป็นได้ทั้ง unidirectional/bidirectionalเส้นทึบ actor ↔ ellipse
«extends» (Extension use case)ดึงขั้นตอนออกจาก use case เดิมเพื่อความเรียบง่าย — เพิ่มฟังก์ชันให้ต้นฉบับ · มักไม่ระบุในเฟส requirements · ลูกศรจาก extension → ต้นฉบับเส้นประ + «extends»
«uses» / «includes» (Abstract use case)รวมขั้นตอนซ้ำกันของหลาย use case ไว้ที่เดียว (ลด redundancy) · มักไม่ระบุในเฟส requirements · ลูกศรจาก ต้นฉบับ → abstractเส้นประ + «uses»
«depends on»บอกว่าต้องทำ use case ใดก่อน — ช่วยจัดลำดับการพัฒนาเส้นประ + «depends on»
Inheritance (ของ actor)สร้าง abstract actor รวมพฤติกรรมร่วม — actor อื่นสืบทอดปฏิสัมพันธ์นั้น (ลด redundancy)ลูกศร → abstract actor
🧠 กฎ include vs extend (จาก elicitation handout — เข้าใจลึกไว้)

«include»: แสดง commonality — base ต้องใช้ included (เช่น ถอนเงิน/ฝากเงิน/พิมพ์ statement ต่าง include "Identify Customer") · ใช้แทนการซ้ำรายละเอียด · เมื่อ included เสร็จ control กลับ base

«extend»: ทำให้ optional/exceptional ชัดเจน — base เดินได้โดยไม่มี extension · ต้องมี extension points + condition · ใช้อย่างประหยัด (sparingly) · ชื่อ use case แบบ Verb-Noun · หลีกเลี่ยง functional decomposition ซ้อนลึก · "If in doubt, leave it out" — ข้อความบรรยาย (text) สำคัญกว่าไดอะแกรม · ห้ามพรรณนา UI ใน use case

4. ขั้นตอน Requirements Use-Case Modeling (4 ขั้น)

  1. Identify business actors — ถาม: ใคร/อะไรให้ input? รับ output? ต้องเชื่อมระบบอื่นไหม? มี event อัตโนมัติตามเวลาไหม? ใครดูแลข้อมูล? · ตั้งชื่อด้วยคำนาม
  2. Identify business requirements use cases — ถาม: งานหลักของ actor คืออะไร? เขาต้องการ/ให้ข้อมูลอะไร? ระบบ/actor ต้องแจ้งเหตุการณ์อะไรแก่กัน? · เน้นessential use cases (critical/complex) ที่ปลอด technology · ตั้งชื่อด้วยกริยา+เป้าหมาย (Submit Subscription Order)
  3. Construct use-case model diagram
  4. Document use-case narratives — เขียน high-level ก่อน (เห็นภาพรวม+ขนาด) แล้วขยายเป็น expanded (typical course + alternate courses)

เทมเพลต use case (ฟิลด์มาตรฐาน): Identifier · Name (verb-object) · Authors · Goal · Preconditions · Postconditions (รวม minimal guarantee) · Primary actor · Participants/Secondary actors · Related requirements/use cases · Description of events (scenarios) · Trigger · Summary · Steps · Special requirements

5. Use Case + Project Management

  • Use-case ranking & priority matrix: ให้คะแนน 1-5 ต่อ 6 เกณฑ์: ① กระทบสถาปัตยกรรมมาก ② ทำง่ายแต่ฟังก์ชันสำคัญ ③ มีความเสี่ยง/time-critical/ซับซ้อน ④ มี research/เทคโนโลยีใหม่-เสี่ยง ⑤ เป็นหน้าที่ธุรกิจหลัก ⑥ เพิ่มรายได้/ลดต้นทุน
  • Use-case dependency diagram: ภาพความ depend กัน — ช่วยเข้าใจฟังก์ชัน · หา use case ที่หายไป · เห็นตัวไหน critical กว่ากัน

6. Misuse Case — มุมมองคนร้าย (จาก elicitation handout)

📖 แนวคิด (Sindre & Opdahl)

Misuse case = use case ที่คุกคามระบบ — เป้าหมายจากมุม "misactor" (ผู้ไม่หวังดี: แฮกเกอร์, คู่แข่ง, พนักงานทุจริต) · ใช้กับ security & risk analysis (Murphy's Law: อะไรที่พังได้ จะพัง)

ความสัมพันธ์: threatens (misuse → use) · mitigates (use → misuse) (+ aggravates, conflicts with ใน trade-off) · สัญลักษณ์ ellipse กลับสี

3 ขั้นหา misuse: ① หา misactors จาก use case diagram ปกติ ② หาว่า misactor จะทำอะไร (misuse cases + threatens) ③ ถามว่าอะไรกลบความเสี่ยง (mitigates) → เพิ่ม included use case/extension/scenario ใหม่ · ตัวอย่าง: "Steal the Car" threatens "Drive the Car" → mitigate ด้วย "Lock the Car", "Lock the Transmission"

⚠️ ระวัง: อย่าตกไปออกแบบทางออกเร็วเกิน (เป้าหมายคือหา requirements) · มุมมองบางส่วนอาจพลาด misactor/ threats

สรุปท้ายบท

✅ ต้องจำให้ได้
  1. Actor 4 ชนิด: business / system / external server / external receiver · temporal event → actor = Time
  2. Association (หัวลูกศร=ผู้เริ่ม) · «extends» (ทางเลือก) · «uses/includes» (ส่วนร่วม) · «depends on» · inheritance
  3. 4 ขั้น: หา actors → หา use cases → วาด diagram → เขียน narrative (high-level → expanded)
  4. Ranking matrix 6 เกณฑ์ + dependency diagram
  5. Misuse case: misactor / threatens / mitigates — เพื่อ security requirements
