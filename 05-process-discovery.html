บทที่ 5 · Process Discovery & คุณภาพโมเดล

ก่อนจะวาด BPMN ได้ ต้อง "ค้นพบ" กระบวนการจริง ๆ ก่อน — บทนี้คือวิธีเก็บข้อมูล วิธีสร้างโมเดลทีละขั้น และเกณฑ์ตรวจว่าโมเดล "ดี" หรือไม่ (อ้างอิงหนังสือ Fundamentals of BPM โดย Dumas et al.)

1. Process Discovery คืออะไร มี 4 งานหลัก

  1. Defining the setting — รวมทีมที่จะรับผิดชอบบริหารกระบวนการ
  2. Gather information — สร้างความเข้าใจกระบวนการ ด้วยวิธี discovery หลากหลาย
  3. Conduct the modeling — ลงมือสร้างโมเดลจริง
  4. Assure model quality — รับประกันว่าโมเดลผ่านเกณฑ์คุณภาพ

ทั้ง 4 งานนี้ทำร่วมกันตลอด (Done together) · คนที่เกี่ยวข้อง: Process Analysts (ฝั่งวิเคราะห์) + Domain Experts (ฝั่งผู้รู้งานจริง)

3 ความท้าทาย (Challenges) ของการ Discovery

1️⃣ Fragmented Process Knowledge

ความรู้กระบวนการกระจัดกระจาย — ไม่มีใครรู้ทั้งกระบวนการ แต่ละคนรู้เฉพาะชิ้นของตัวเอง

2️⃣ Experts คิดระดับ "instance"

Domain expert มักเล่าเหตุการณ์รายกรณี (instance) ที่ตัวเองเจอ ไม่ใช่ภาพรวมกระบวนการ (process level)

3️⃣ ความรู้การทำโมเดลหายาก

คนทั่วไปไม่คุ้นกับสัญลักษณ์โมเดล — "ไดอะแกรมนี้ถูกต้องไหม" ถามตรง ๆ มักไม่ค่อยได้คำตอบที่มีประโยชน์

💭 จ้างใครดี? George vs Sarah (แบบฝึกในเอกสาร)

George ประสบการณ์ 10 ปีกับร้านค้าออนไลน์ (รู้งานลึก แต่เป็น domain expert) · Sarah ประสบการณ์นักวิเคราะห์กระบวนการ 5 ปีในธนาคาร (รู้จักภาษาโมเดล + เครื่องมือ) — เฉลยแนวคิด: งานนี้คือ "นักวิเคราะห์กระบวนการ" Sarah มีทักษะ abstraction และ modeling ที่จำเป็น ส่วน George เก่งเรื่อง domain แต่คิดเป็น instance และอาจมี bias จากที่เคยทำ

คุณสมบัติของ Process Analyst ที่เก่งงาน (4 ข้อ)

  1. Getting the right people on board — ดึงคนที่ใช่เข้าทีม
  2. Having a set of working hypotheses — มีสมมติฐานว่ากระบวนการน่าจะเป็นอย่างไร หลายระดับความละเอียด แล้วทดสอบมัน
  3. Identifying patterns — มองเห็นแพทเทิร์นในข้อมูลที่ผู้เชี่ยวชาญบอก
  4. Paying attention to model quality

2. Discovery Methods — วิธีเก็บข้อมูล 3 กลุ่ม

Observationเห็นบริบทจริงลึกซึ้ง (context-rich)อาจรบกวนการทำงาน (intrusive) · คนถูกสังเกตทำตัวผิดธรรมชาติ · เห็นเพียงไม่กี่เคส

📋 รายละเอียดแต่ละวิธี
  • Document Analysis — อ่าน: process descriptions (ดีที่สุดถ้ามี), internal policies, org charts, employment plans, quality reports, glossaries/handbooks, forms, work instructions · ใช้เก็บข้อมูลก่อนเข้าพบ domain experts ได้
  • Observation — ตามดูการทำงานรายเคส แล้วยกระดับจาก instance → process: บทบาท Active (เล่นบทบาทจริง เช่น เป็นลูกค้า — เสี่ยง: เห็นแค่ภาพเล็ก) / Passive (สังเกตผู้ปฏิบัติ+สิ่งแวดล้อม — เสี่ยง: bias ของคนถูกสังเกต) · ตามรอย business object ตลอด life cycle
  • Interview — แนว Forward (ไล่ตั้งแต่เริ่มกระบวนการ) vs Backward (ย้อนจากผลลัพธ์) · Structured (คำถามตามแบบ) vs Unstructured · กับดัก: พฤติกรรม exception มักถูกละเลย → ตั้งคำถามเจาะหา exception โดยเฉพาะ
  • Workshop — รวม key stakeholders ทั้งหมด มี process analyst 1 คนเป็น facilitator + domain experts หลายคน (process owner อาจร่วมด้วย) · อาจมี tool operator วาดโมเดลสด ๆ · ทางเลือก: brown-paper workshop · ปกติ 3-5 ครั้ง ครั้งละครึ่งวัน

3. วิธีสร้างโมเดลทีละขั้น (Stepwise Modeling Method)

  1. Identify the process boundaries — จุดเริ่ม/จบ: Trigger คืออะไร? ผลลัพธ์บวก/ลบคืออะไร? มองจากมุมไหน (perspective)? ต้องใช้/ผลิตเอกสารอะไร (input/output)?
  2. Identify activities and events — เอากิจกรรม+เหตุการณ์ออกมาให้ครบ
  3. Identify resources and their handovers — ใครทำ ส่งงานต่อกันตรงไหน
  4. Identify the control flow — ลำดับ เงื่อนไข ทางแยก
  5. Identify additional elements — data objects, ชนิด events พิเศษ, exception handling
🎯 ตัวอย่างการหา Boundaries (Order-to-Cash)
  • Trigger: Purchase order received (ได้รับใบสั่งซื้อ)
  • Positive outcome: Order fulfilled (ส่งมอบสำเร็จ) · Negative outcome: Order rejected (ปฏิเสธคำสั่งซื้อ)
  • Perspective: Seller (มองจากฝั่งผู้ขาย — มุมมองลูกค้าจะต่างออกไป!)
  • Input: Purchase Order · Outputs: Invoice, Shipment notice

4. คุณภาพโมเดล (Model Quality Assurance)

Structural Correctness (กฎโครงสร้าง)

  • Element-level: กิจกรรมต้องมี sequence flow เข้าอย่างน้อย 1 + ออกอย่างน้อย 1 · Start ห้ามมีเส้นเข้า · End ห้ามมีเส้นออก · Gateway แบบ split ต้องมีเข้า 1 ออก ≥2 · แบบ join เข้า ≥2 ออก 1
  • Model-level: ทุก node ต้องอยู่บนเส้นทางจาก start → end (ไม่มี node ลอย ๆ หรือเส้นหลุด)

Behavioral Correctness = "Soundness" (เสียง 3 ข้อ — ออกสอบ!)

  1. Option to complete — process instance ใด ๆ ที่เริ่มแล้วต้องจบได้เสมอ (ไม่ติด deadlock/livelock)
  2. Proper completion — ตอนจบ ต้องมี token เพียงอันเดียวใน end event (ไม่มี token ค้างซ้อน = lack of synchronization)
  3. No dead activities — ทุกกิจกรรมต้องมีโอกาสได้ทำอย่างน้อยหนึ่ง instance (ห้ามมีกิจกรรมที่ทำไม่ได้กันหมด)
⚠️ กับดักมือใหม่ (Beginner's Mistake)

จับคู่ gateway ผิดประเภท — เช่น เปิดด้วย AND-split แต่ปิดด้วย XOR-join (หรือ XOR-split + AND-join) → เกิด deadlock/livelock เสมอ · กฎทับทิม: แต่ละ split จับคู่กับ join ชนิดเดียวกัน (model in blocks)

7PMG — 7 Process Modeling Guidelines (แนวปฏิบัติ 7 ข้อ)

#กฎความหมาย
G1ใช้ elements ให้น้อยที่สุดโมเดลเล็กยิ่งอ่านง่าย
G2ลด routing paths ต่อ elementเส้นทางยิ่งน้อยยิ่งเข้าใจง่าย
G3Start event 1 อันต่อ trigger · End event 1 อันต่อ outcomeแยกตามเหตุการณ์เริ่ม/ผลลัพธ์
G4วาดโมเดลให้เป็น blocks ที่มีโครงสร้างsplit-join จับคู่กันเป็นบล็อก
G5เลี่ยง OR gateway ถ้าทำได้semantics ซับซ้อน เสี่ยงสับสน
G6ใช้ label Verb + Object"Issue Driver Licence" ไม่ใช่ "ทำ"
G7โมเดลเกิน 30 elements → แตกเป็น subprocessรักษาความเข้าใจง่าย

สรุปท้ายบท + สรุปเรื่อง Events/Exceptions (จากท้ายเอกสาร)

✅ ต้องจำให้ได้จากบทนี้
  1. Discovery 4 งาน: setting → gather → model → quality · คน: Process Analyst + Domain Expert
  2. 3 ความท้าทาย: ความรู้กระจัดกระจาย · expert คิดระดับ instance · คนไม่คุ้นโมเดล
  3. วิธี 3 กลุ่ม (Evidence / Interview / Workshop) + ตารางจุดแข็ง-จุดอ่อน + automated discovery ต้องมี Activity+Timestamp+CaseID
  4. วาดโมเดล 5 ขั้น: boundaries → activities/events → resources/handovers → control flow → เพิ่มเติม
  5. คุณภาพ 3 ชั้น: Syntactic (Verification) / Semantic (Validation: Valid+Complete) / Pragmatic (Certification)
  6. Soundness 3 ข้อ: option to complete · proper completion · no dead activities
  7. 7PMG (โดยเฉพาะ G5 เลี่ยง OR, G6 Verb+Object, G7 ไม่เกิน 30 elements)

เกร็ดเพิ่มเติมท้ายเอกสาร: loop แบบมีโครงสร้างใช้ loop activities ได้ แต่รอบ arbitrary ไม่ได้ · intermediate events เป็น catching หรือ throwing · timer events = เหตุการณ์ตามเวลา (จับเวลา/เป็นระยะ) · จัดการ exception ง่ายสุดด้วย terminate event · boundary error/message/timer events ใช้จับ exception ภายใน/ภายนอก/timeout · compensation events ใช้ย้อนผลของงานที่เสร็จแล้ว · conditional events ใช้แทน business rules ได้
